## C. `relationship_legacy_event_invalid` 什么条件下抛？是我们的接口缺还是插件业务数据？

**结论：插件自身"写入词表 vs 回放校验词表"不一致。不是兼容层缺接口，也不是我们的数据被改写。**

### C.1 抛出点与全部前置条件

`relationship_account_store.py:622-656`（`replay_legacy_event`）：

```python
context = self._authorize(context, "relationship_write")
...
totals, effective = self._validated_legacy_runtime(daily_totals, last_effective_at)   # 另一个错误码
if (
    context.kind != "private" or not event
    or reason not in (PRIVATE_EVENT_REASONS | frozenset({GROUP_DIRECT_REASON}))
    or None in {requested, applied, before, after} or applied == 0
    or after - before != applied or not -1200 <= before <= 1200 or not -1200 <= after <= 1200
    or role not in ACCOUNT_ROLES or mode not in ACCOUNT_MODES
    or normalize_relationship_mode(mode, role) != mode
):
    raise RelationshipStoreError("relationship_legacy_event_invalid")     # ← :656
```

### C.2 哪一个谓词挂了（实测对照）

只读 dump `req041_migration_outbox.db`，全库只有 **1 条 `state='failed'`**：

```

error_code=relationship_legacy_event_invalid      created_at=1789883660.285838 (=2026-09-20 13:54:20 CST)
namespace_json: {"kind": "private", "group_id": "", "identity_id": "person_023d8c...", "assurance":"verified", "profile_status":"active", ...}
payload_json:   {"applied_delta":1, "daily_totals":{"day":"2026-09-20","negative":0,"positive":1},
                 "event_key":"328d369c6d847215edf825d4", "group_admission_event_ref":"",
                 "reason_code":"fast_inbound", "relationship_mode":"normal", "relationship_role":"friend",
                 "requested_delta":1, "score_after":1, "score_before":0, "operation":"relationship_legacy_event", ...}
```

逐条对 C.1 的谓词：

| 谓词 | 该 payload | 结果 |
|---|---|---|
| `context.kind != "private"` | `"private"` | 通过 |
| `not event` | `event_id` = outbox 主键，非空 | 通过 |
| **`reason not in (PRIVATE_EVENT_REASONS ∪ {direct_group_interaction})`** | **`fast_inbound`** | ❌ **唯一挂掉的** |
| `None in {requested, applied, before, after}` | 1/1/0/1 | 通过 |
| `applied == 0` | 1 | 通过 |
| `after - before != applied` | 1-0 == 1 | 通过 |
| 分数区间 | 0/1 ∈ [-1200,1200] | 通过 |
| `role ∉ ACCOUNT_ROLES` / `mode ∉ ACCOUNT_MODES` | `friend`（:43）· `normal`（:44） | 通过 |
| `normalize_relationship_mode("normal","friend") != "normal"` | `relationship_ledger.py:67-72` 返回 `normal` | 通过 |

而 `PRIVATE_EVENT_REASONS`（`relationship_account_store.py:47-66`）里只有 **`inbound`**，没有 `fast_inbound`。

### C.3 这个 `fast_inbound` 是谁产生的（归属判定）

* **产生处是插件自己的代码**：`message_pipeline.py:446`
  `self._apply_relationship_event(fast_user, 1, reason_code="fast_inbound", event_id=..., now=...)`，
  位于 `async def handle_private_message`（`message_pipeline.py:109`，私聊消息处理主入口）。
  同类别名还有 `fast_proactive_reply`（`:468`）、`fast_interaction_warmth`（`:516`）；
  同一文件**另一条**路径用的是规范词 `inbound`（`:858`）、`proactive_reply`（`:891`）。
* **插件自己知道这是别名**：`relationship_ledger.py:35-39`
  `_EVENT_REASON_ALIASES = {"fast_inbound": "inbound", "fast_proactive_reply": "proactive_reply", "fast_interaction_warmth": "interaction_warmth"}`，
  用在 `:268`/`:626`（去重与 event_key 计算）——但**入账与入队都保留原词**。
* **原样进 outbox 的路径**：`core_store.py:5089-5098`
  `producer.emit_relationship(..., reason_code=str(reason_code or ""), ...)`
  → `migration_dual_write.py:166` `reason = _token(reason_code, 48)` → `:184` `"reason_code": reason`
  （**没有任何归一化**）。
* **不是我们改写的**（关键反证）：插件自己的 legacy 账本 `companions.json` 里，同一个 `event_key`
  存的**也是原词**：
  ```json
  {"event_key": "328d369c6d847215edf825d4", "reason_code": "fast_inbound",
   "delta": 1, "score_before": 0, "score_after": 1, "created_at": 1789883660.2653923}
  ```
  ⇒ 我们这边既没有把 `inbound` 改成 `fast_inbound`，也没有反过来；两侧词表本来就一致，**是回放校验器不认自己写的词**。
* **失败后的连锁**：`migration_replay.py:379-394 _fail_closed()`
  → `outbox.mark_failed(...)` + `coordinator.pause(code)`（`migration_coordinator.py:811-818`：`state='paused', error_code=...`）
  + `outbox.set_epoch_state(epoch, "degraded", checkpoint=code)`。
  与实测完全对上：控制行 `state=paused / error_code=relationship_legacy_event_invalid`；
  outbox `migration_epochs` 行 `state='degraded' / checkpoint='relationship_legacy_event_invalid'`；
  outbox 计数 `applied=1 / failed=1 / pending=63`（`req041.outbox` 线上读数一致）。

`reason_code` 的选词、归一化、入队、校验全在插件内部完成。

## D. 要让「身份与隔离 → 归档」可用（`ready == True`），需要满足什么？

### D.1 条件集（代码级，唯一入口）

`page_api_users_groups.py:385-404 _identity_archive_status()` 判定链：

```
_identity_archive_remote_available()            (:373-383)
   └─ plugin._req041_scoped_archive_available() (main.py:7248-7260)
        ├─(1) plugin.req041_scoped_projection_sync 非空 且 archive_identity_scopes 可调用
        └─(2) plugin.req041_migration_status["state"] ∉ {"degraded","paused","stopped"}
若 ready=False：
   ├─ 同步器不存在 → code=scoped_archive_bridge_unavailable（"未连接…记忆桥接服务"）
   └─ 同步器存在   → code=scoped_archive_<state> / scoped_archive_not_ready
```

线上现状：**(1) 已满足**（否则 archive_code 会是 `scoped_archive_bridge_unavailable`），
**(2) 不满足**（`state='degraded'`）⇒ `ready=False`。

### D.2 为什么 state 进不了健康区间（两条独立的锁）

线上 `req041.state` 的**唯一**写入者：`main.py:6570`
（`grep "scoped_projection_degraded"`：只有 `:6409` 是 summary 文案、`:6570` 才是写状态）
—— 即 `_req041_run_scoped_sync()`（`main.py:6563-6571`）观察到 `_req041_sync_scoped_now()` 返回 `ok=False`。

要让 state 变健康，`_req041_run_memory_scope_rebind()`（`main.py:6543-6558`）要求**同时**：

* `result.get("ok")`（本次 scoped 同步成功）；
* `status["state"] != "paused"`；
* `replay_ready = not required or status["s5"]["status"] == "ok"`。

而实际卡在：

1. **控制行已 paused，且插件不会自动 resume**：`start_or_resume()`（`migration_coordinator.py:338-392`）
   在已存在控制行时**只校验合约与备份、然后返回 `self.status()`**；唯一把状态改回 `replaying` 的是
   `resume()`（`:820-828`）——
   **全插件（非测试代码）`grep "\.resume()"` 为空、`grep "start_or_resume"` 只有 `main.py:8060` 一处（启动）**
   ⇒ **迁移一旦 paused 就是终态，插件自己没有任何恢复路径（连面板按钮都没有，见 §F.3）**。
   每次启动走到 `main.py:8082-8087` 就直接 `return`（连回放/回填都不跑），因此 `runtime["s5"]` 在本轮**根本没被写**，
   `replay_ready` 恒为 False。
2. **state 是"粘性"的**：`_req041_run_memory_scope_rebind()`（`main.py:6543-6558`）只有在
   `result.ok 且 not paused 且 replay_ready` 时才把 state 改成 active；任一不满足就 `return`，
   **永远不会把 degraded 清掉**。而 `mark_dirty()`（`migration_scoped_projection.py:163-171`）会在每次
   同步前**清空** `_ready_scopes` 与投影缓存，同步一失败缓存就一直是空的
   （线上实测 `scoped_projection` 缓存 `size=0 / hit=0 / stale_reject=514`）⇒
   插件的 scoped 读每次都返回 `scoped_projection_not_reconciled`（`migration_scoped_projection.py:653-664`）。
   → 附带影响：**不只是删不掉用户**，插件的统一人物 scoped 读取也一直处于不可用状态。
3. **同步当前仍在失败（有实测证据）**：见 §F.1 —— 记忆桥那一侧的 `req041_scoped.db` 里
   60 条 `created` + 1 条 `updated`、**0 条失败**，但投影缓存始终为空、0 次 hit ⇒
   每次同步都有 **个别** 调用失败（`counts["errors"] > 0`），不是"整条桥不可用"。
   具体是哪一条，见 §F.1 的"拿不到"。

### D.3 哪些是兼容层能补的？哪些不是？

| 条件 | 归属 | 证据 |
|---|---|---|
| 调用插件 `initialize()`（让后台任务被创建） | **兼容层**，**已做到** | `host_app.py:202-205,245-247`；`plugin_host.py:429-434`；`.env:59` |

## E. 新会话（方案 B：一会话一 umo）建档后，会不会也带上 `unified_person_id`？

**结论：会。只要那个会话真的聊过一句，该插件用户就会被绑定到统一人物，删除按钮就走归档闸门。**

  `create_unified_person_for_event(...)` 现建一个人物，再回填 `unified_person_id`。
* **私聊的正常触发路径**：`message_pipeline.py:132-148`，在
  `_ensure_auto_private_user_profile(...)` 之后**无条件**调用
  `self._req036_attach_unified_profile_context(event, user=private_user, source="private_auto")`
  —— 也就是**每条私聊入站消息**都会走（`handle_private_message`，`message_pipeline.py:109`）。

* **线上实测（一有一无，正是"有没有聊过"的差别）**：
  `GET /page/users`（20 个用户）：
  ```
  sess-68c74ee1126d → unified_person_id = person_72191c7c70ee315458db6a83   ← 有
  sess-659b4e15af8b → unified_person_id = ""                                 ← 无
  ```

⇒ **对产品的含义**：方案 B 让每个会话成为独立插件用户，而插件对这些用户是 **auto 建档 + 自动绑定统一人物**
（`compatibility_json.auto_profile_creation = true`），因此"每个会话产生的用户都删不掉"**是当前设计的必然结果**，
不是偶发 bug。要能删测试用户，必须在**数据链层面**决定（走归档流程，或改变测试会话的建档策略），
而不是在删除按钮上打补丁。

### F.2 `relationship_legacy_event_invalid` 是谁的问题？—— **插件业务数据本身不合法**

**判定依据（三段推理，全部有代码位置 + 磁盘实证）**：

1. **抛出点在插件的回放校验器**：`relationship_account_store.py:622-656`（`replay_legacy_event`），
   挂掉的谓词是 `reason not in (PRIVATE_EVENT_REASONS | {"direct_group_interaction"})`（`:647-655`、`:656`）。
   `PRIVATE_EVENT_REASONS`（`:47-66`）里只有规范词 `inbound`，**没有** `fast_inbound`。
   其余谓词按 payload（`applied=1 / before=0 / after=1 / role=friend / mode=normal / kind=private`）**全部通过** ——
   见 §C.2 的逐条对照表。
2. **这个 `fast_inbound` 是插件自己写的**：产生处 `message_pipeline.py:446`
   （`handle_private_message`，`:109`）；插件自己的 legacy 账本 `companions.json` 里同一个 `event_key`
   `328d369c6d847215edf825d4` 存的也是 `"reason_code": "fast_inbound"` ⇒ **我们既没改词也没丢字段**。
   别名表 `relationship_ledger.py:35-39` 明明有 `fast_inbound → inbound`，但只用在去重/event_key（`:268`/`:626`），
   **没有用在入队与校验**：`core_store.py:5089-5098` 把原词交给 `migration_dual_write.py:166,184` 原样入 outbox。
3. **失败后是插件自己的 fail-closed**：`migration_replay.py:379-394 _fail_closed` → `coordinator.pause(code)`
   （`migration_coordinator.py:811-818`）+ outbox `mark_failed` + `set_epoch_state(degraded)`。
   与磁盘完全一致：控制行 `state=paused / error_code=relationship_legacy_event_invalid`，
   outbox `migration_epochs` 行 `state=degraded / checkpoint=relationship_legacy_event_invalid`，
   计数 `applied=1 / failed=1 / pending=63`。

**⇒ 不是兼容层缺接口**：我们只提供"有一条私聊消息"这个事件；`reason_code` 的选词、归一化、入队、校验
