# 「有 UI、能保存、零消费点」字段清单（2026-10-09 实扫）

> 起因：情绪发现「设置页配置的对话模型」和「测试连接秒回正常」两处不对，
> 于是要求**把同类的假能力全面扫一遍**。
>
> 工具：`tools/fake_capability_scan.py`（可重跑）。
> 口径见该文件头部注释 —— **三条排除规则**（定义处 / 泛型搬运 / 测试与前端），
> 否则会大面积误报。

## 判据口径（为什么这么定）

一个字段被引用，有四种性质完全不同的"引用"：

| 性质 | 算不算"被消费" | 例 |
|---|---|---|
| **声明** | ❌ 不算 | `config_profile.SPECS` 里的 `FieldSpec(key=...)` |
| **泛型搬运** | ❌ 不算 | `to_dict()` / `validate_patch()` / `patch()` —— 它们对**所有**字段一视同仁 |
| **测试与前端** | ❌ 不算 | `tests/`、`static/app.js`（前端只负责渲染，不构成"后端用了它"） |
| **真实消费** | ✅ 算 | 业务代码里读了它、行为随它变 |

⚠️ **如果不做这三条排除，"假能力"会几乎全是误报**（泛型搬运对每个字段都会命中一次）。

## 结果总览

```
schema 字段总数：23
  有消费点：6
  🔴 零消费点：17
```

**17 个里要分成三类看**，别一律当 bug：

---

## A 类 —— 🔴 **真缺口**（文案承诺了能力，但没有实现）

| 字段 | 界面文案（**承诺**） | 实际 | 严重度 |
|---|---|---|---|
| `default_chat_provider_id` | 「留空时使用第一个可用模型。**插件与面板都按它选模型。**」 | **零消费点**。插件与面板都不按它选 —— 真正决定模型的是「上游连接」那块运行时设置 | 🔴 高 |
| `fallback_chat_provider_ids` | 「主对话模型请求失败时，**按顺序切换到这些模型**。」 | **零消费点**。没有任何回退逻辑 | 🔴 高 |
| `display_reasoning_text` | 「开启后会**显示模型的推理内容**（如果模型支持）。」 | **零消费点** | 🟡 中 |
| `datetime_system_prompt` | 「开启后会**在系统提示词中附带当前时间信息**。」 | **零消费点** | 🟡 中 |
| `streaming_response` | 「我们默认**开**（本来就有流式）」 | **零消费点**。文案**没说它会生效**，但也没说它不会 —— 用户关掉它不会有任何变化 | 🟡 中 |

⚠️ **A 类前两条是本轮情绪点名要接线的**（见下节）。
⚠️ `default_chat_provider_id` 的文案里那句「插件与面板都按它选模型」是**明确的事实陈述**，
   而它不是真的 —— 这类"文案说了一件不存在的事"比字段空着更糟。

---

## B 类 —— ✅ **诚实标注了未实现**（文案已说明，不算 bug）

| 字段 | 文案里的免责说明 |
|---|---|
| `tts_enable` | 「⚠️ 本轮只保存配置，**暂不出声**」 |
| `tts_trigger_probability` | 「（将来真出声时生效）」 |
| `default_tts_provider_id` | 「留空 = 不指定」（同组已标注 TTS 未实现） |
| `stt_enable` | 「⚠️ 只保存配置，**暂不转写** —— 我们还没实现 STT 适配器」 |
| `default_stt_provider_id` | 「⚠️ 目前列出的模型本平台都还不能真跑（配置先行）」 |

**这五个是"提前占位"，不是缺陷** —— 项目明确说了"配置先行"（意图是先把配置面做全，
将来补链路时不用改 schema/前端）。**保持现状，不动。**

---

## C 类 —— ⚠️ **另一套并行的全局配置**（既不是假能力，也不是已实现）

| 字段 | 情况 |
|---|---|
| `max_context_length` | 全局 schema 里有，**但聊天真正读的是「会话级」的 `session.policy`** |
| `dequeue_context_length` | 同上 |
| `context_limit_reached_strategy` | 同上 |
| `llm_compress_instruction` | 同上 |
| `llm_compress_keep_recent_ratio` | 同上 |
| `llm_compress_provider_id` | 同上 |
| `fallback_max_context_tokens` | 同上 |

**根因**：上下文策略有**两套并行的配置面**——

* **会话级**：`session.policy`（`session_repo.py:68` 的 `ContextPolicy`），**聊天真正读它**
  （`chat.py:514` → `build_context(all_msgs, session.policy, ...)`）；
  只有 `mode` / `protected_tail` / `summary_trigger` 三个字段有消费点。
* **全局**：`config_profile.context`（设置页「配置文件」那段渲染的），
  **7 个字段一个都没被读**。

⇒ 用户在设置页改全局上下文策略，**不会影响任何会话**；
   而会话页那套（`mode`/`protected_tail`/`summary_trigger`）才是真的。

⚠️ 这就是本项目「**同一概念多条写入路径**」的**第 7 次**，且形态是"两套配置面各自完整、
   但只有一套接线" —— 比"同一个字段两条路径"更难发现，因为两边的字段名大部分**不同**。
