- 日期：2026-09-27
- 任务：查清面板 iframe 打开的插件拓展页为什么报 404。**只诊断，未改任何产品代码。**
- 环境：`/root/Ai-works/情绪app`，服务在跑 `http://127.0.0.1:6191`（pid 3905246）。
- 复现用的登录 cookie：`/tmp/ck3.txt`（下文所有 curl 都带 `-b /tmp/ck3.txt`）。

## 0. 结论

**404 的确切 URL**（content_companion 页面自己拼出来的）：

```
GET /api/plug/astrbot_plugin_content_companion/page/status      → 404
GET /api/plug/astrbot_plugin_content_companion/page/projects    → 404
GET /api/plug/astrbot_plugin_content_companion/page/feed        → 404（点「读取动态」时）
```

**根因一句话**：该插件页 JS **硬编码**了 `const API = "/api/plug/<插件名>/page"`（真 AstrBot 4.27.5 里确有这条
legacy 路由 `dashboard/api/plugins.py:1506`，**我们没实现**），于是请求既没命中我们的插件派发器
（我们的形状是 `/api/plugins/extensions/...`），又被我们**自己的兜底路由的保留前缀守卫**
（`emotion_app/web/plugin_pages_web.py:190-192`）在**鉴权之前**直接 404 掉，**且不留任何日志**。

**三条子问题逐条回答**：

| 问 | 答 | 证据 |
|---|---|---|
| 是路由没挂吗 | **是（这一条）** —— 我们**根本没有** `/api/plug/...` 这条路由 | §2.1 |
| 是插件没注册这个 API 吗 | **否** —— 插件注册了 4 条，宿主已挂载，换个前缀打就是 200 | §2.3 |
| 是桥接垫片把 URL 拼错吗 | **与本 404 无关** —— 该页面**完全不使用垫片**；且垫片拼出的形状本身没错，只是**缺插件目录名那一段** | §2.2 / §5 |

**三个插件页状态**：`qzone-companion` ❌ 全挂（404）、`companion-panel` ✅ 数据能取到、
`一起房间` ❌ 全挂（404）。详见 §3。

## 1. 那个 404 具体是哪个 URL

### 1.1 从插件页 JS 源码找出端点

`data/plugin_src/astrbot_plugin_content_companion/pages/qzone-companion/app.js:1-3`：

```js
const API = "/api/plug/astrbot_plugin_content_companion/page";
const $ = (id) => document.getElementById(id);
async function call(path, options = {}) { const res = await fetch(API + path, {headers:{"Content-Type":"application/json"}, ...options}); const data = await res.json(); if (!res.ok) throw new Error(data.message || `请求失败（${res.status}）`); return data; }
```

调用点（同一个文件）：

- `:8` `loadStatus()` → `call("/status")`
- `:9` `loadFeed()` → `call("/feed")`
- `:10` `loadProjects()` → `call("/projects")`
- `:11` `publish()` → `call("/action")`

⚠️ 注意 `:3` 的错误分支用的是 `data.message`，而我们的 404 body 里**没有 `message` 字段**（只有 `error`/`type`）
→ 于是模板串回落到 `` `请求失败（${res.status}）` `` → 这就是屏幕上那句 **「请求失败（404）」**。

该页面**全文不出现 `AstrBotPluginPage`**（垫片给的桥）：

```console

0
$ grep -c 'AstrBotPluginPage' data/plugin_src/astrbot_plugin_content_companion/pages/qzone-companion/index.html
0
```

⇒ 它是**纯粹的 HTTP 直连**页面，取数 100% 走 `API` 常量。

## 2. 该端点为什么 404：逐层定位

### 2.1 层①：我们的路由表里**没有** `/api/plug/...`

```console
$ grep -n '@app.route\|@app.get' emotion_app/web/*.py
emotion_app/web/app.py:850:    @app.route("/api/plugins/extensions/<path:plugin_path>", methods=methods)
emotion_app/web/plugin_pages_web.py:182:    @app.route("/<plugin_dir>/<path:rest>", ...)
```

我们挂的插件 API 前缀是 **`/api/plugins/extensions/<path:plugin_path>`**（`app.py:850`，
注释里写明"照真实现的路由形状"，`host/astrbot_host/host_app.py:39` `EXTENSION_PREFIX`）。

**真 AstrBot 4.27.5 里有两条**（只读引用生产副本）：

```console
$ sed -n '1506,1514p' /root/.local/share/uv/tools/astrbot/lib/python3.12/site-packages/astrbot/dashboard/api/plugins.py
@legacy_router.api_route("/api/plug/{plugin_path:path}", methods=["GET", "POST"])
async def dashboard_plugin_extension_route(
    plugin_path: str,
    request: Request,
    username: str = Depends(require_dashboard_user),
):
    return await _call_plugin_extension(plugin_path, request, username)
```

⇒ 插件作者写 `const API = "/api/plug/<插件名>/page"` **在真 AstrBot 上是对的**（内存插件页 app.js:8-11
的注释也印证：*"/api/plug route is available across dashboard versions"*）。我们只实现了
`/api/plugins/extensions` 那条，**漏了 `/api/plug` 这条 legacy 兼容路由**。

### 2.2 层②：那 41 字节的 404 不是"没匹配到路由"，是**我们自己的守卫**打的

框架自身的 404 handler（`emotion_app/web/app.py:650-662`）打的是**另一种 body**：

```console
$ curl -s -b /tmp/ck3.txt 'http://127.0.0.1:6191/zzz'
HTTP 404 71B 
{"error":{"message":"Not Found: /zzz","type":"invalid_request_error"}}
```

而实测 `/api/plug/...` 的 body 是 `{"error":"not found","type":"not_found"}`，**这个字面量在项目里只有一个出处**：

```console
$ grep -rn '"not found", "type": "not_found"' emotion_app/ host/
emotion_app/web/plugin_pages_web.py:192:            return jsonify({"error": "not found", "type": "not_found"}), 404
```

即兜底路由 `/<plugin_dir>/<path:rest>`（`plugin_pages_web.py:182`）里的**保留前缀守卫**：

```python
# emotion_app/web/plugin_pages_web.py:37-43
RESERVED_PREFIXES = ("api", "static", "health", "v1", "favicon.ico")
...
# :190-192
if plugin_dir in RESERVED_PREFIXES:
    # 正常不该走到这（具体路由优先），但显式挡一道更安全
    return jsonify({"error": "not found", "type": "not_found"}), 404
```

**逐字节核对**（`/tmp/q1.txt` 是 curl 落盘的原始 body）：

```
源码字面量长度: 40 bytes(utf8): 40
实测 body 原始字节: b'{"error":"not found","type":"not_found"}\n'
实测长度: 41  与 jsonify 只差一个换行? True
```

**位置证据**：`/api/plug/astrbot_plugin_content_companion/page/status` 的
`plugin_dir = "api"`、`rest = "plug/astrbot_plugin_content_companion/page/status"`
→ `"api" in RESERVED_PREFIXES` 为真 → 命中 `:192`。

**鉴权顺序证明**：`:190` 的守卫在 `:194` 的 `require_auth()` **之前** return
⇒ 所以**无 cookie 也是 404 而不是 401**。反证（对照）：

```console
$ curl -s -o /dev/null -w '%{http_code}\n' 'http://127.0.0.1:6191/astrbot_plugin_content_companion/page/status'   # 无 cookie
401
$ curl -s -o /dev/null -w '%{http_code}\n' 'http://127.0.0.1:6191/api/plug/astrbot_plugin_content_companion/page/status'  # 无 cookie
404
```

—— 走到派发器的那条路（非保留前缀）无 cookie 会 401，被守卫挡下的这条不会。**证明请求确实到达了我们的应用**，
不是被 hypercorn/Hypercorn 路由层丢弃。

## 4. 「数据模式 已挂载 / 沿用旧数据兼容迁移」是什么意思

**答案：它是一段写死在 HTML 里的静态文案，没有任何 id，`app.js` 从不碰它 —— 不判断任何字段，不调任何接口。**

证据一，页面源码（`data/plugin_src/astrbot_plugin_content_companion/pages/qzone-companion/index.html:38`）：

```html
<article class="card metric"><span>数据模式</span><strong>已挂载</strong><small>沿用旧数据兼容迁移</small></article>
```

—— 对比同一行旁边的两张卡：`<strong id="qzoneState">` 和 `<strong id="projectCount">` **都有 id**（会被 JS 改写），
唯独这两块**没有 id**：

```console
$ grep -o '<span>数据模式</span><strong[^>]*>[^<]*</strong>' .../index.html
<span>数据模式</span><strong>已挂载</strong>
```

证据二，`app.js` 全文找不到这些字面量：

```console
$ grep -n '数据模式\|已挂载\|沿用旧数据\|migrat' data/plugin_src/astrbot_plugin_content_companion/pages/qzone-companion/app.js
（无输出，exit=1）
```

**所以它跟「接口挂没挂」毫无关系** —— 页面 API 全 404 的同一时刻，它照样显示"已挂载"。
（截图里正是这个画面：左卡「不可用 / 请求失败（404）」、右卡「已挂载 / 沿用旧数据兼容迁移」。）

**这个"概念"在后端确实存在**，但页面根本不读它。后端

```python
            "completed": migration_completed,
```

这段字段是通过 `/page/status` 下发的 ——**而 `app.js` 只读了其中一个字段**：

```console
$ grep -n 'managed_by_private_companion\|migration\|data_owner\|mode' .../qzone-companion/app.js
8:async function loadStatus() { try { const payload = await call("/status"); const data = payload?.data || {}; if (data.managed_by_private_companion) { showManagedPage(true); return true; } ...
```

`app.js:8` 只用了 `data.managed_by_private_companion`（决定显示"业务页"还是"已由陪伴插件接管"页），
`mode` / `data_owner` / `migration` **一次都没被读**。⇒ 那张卡是**装饰性硬编码**，如实记录，不做推断。

⚠️ **对修复方向的直接影响**：`/page/status` 现在的实际返回值是
`{"available":false,"enabled":false,"installed":true,"managed_by_private_companion":true,"reason":"private_companion_unavailable"}`

`index.html:27-35` 那块「已由陪伴插件接管」的锁定页**（这正是插件的设计：避免两处配置互相覆盖）。
修 URL 之后看到的样子会和现在不一样，这是**预期行为**，不是新 bug。


- `qzone-companion` 连垫片都不加载。

⇒ 垫片不是这段 404 的成因，但**"同源垫片能替代官方桥"这个前提在候选形状上只对了三分之一**。

## 6. 修复方向候选（**只列选项与取舍，未改任何代码**）

> 前提：以下都不动 `data/plugin_src/**`。插件是外部产物，改它会被升级覆盖，也违反本任务禁令。

### 选项 A（推荐）：补一条 `/api/plug/<path:plugin_path>` 兼容路由

照真实现 `plugins.py:1506` 的形状，挂到同一个派发器（`host.call_api`），与
`app.py:850` 那条并列。**它是比兜底路由更具体的路由，会先命中**，不受 `RESERVED_PREFIXES` 影响。

- ✅ 修好 `qzone-companion`；顺手为 `memory_companion` 未来挂载铺路。
- ✅ 只加路由，不动插件、不动垫片、不动兜底路由。
- ⚠️ **必须带 `require_auth()`**（本项目铁律：新增任何 API 路由先对照隔壁那行的鉴权 ——
  真实现这条是 `Depends(require_dashboard_user)`，我们对应 `require_auth()`）。
- ⚠️ 与 `app.py:850` 会形成**两处代码做同一件事** → 建议抽成同一个 handler 函数，
  别复制粘贴第二份派发+错误处理逻辑（否则"同一概念多条写入路径"再犯一次）。
- 影响面：小。风险：低。

### 选项 B：让垫片从页面 URL 反推 plugin_id

垫片里读 `location.pathname`（`/api/v1/plugins/<plugin_id>/pages/<page_name>/...`）取出 `plugin_id`，
当 `endpoint` 不以它开头时补上一段。

- ✅ 修好 `一起房间`（它走垫片）。
- ❌ **修不了 `qzone-companion`** —— 那个页面根本不调垫片，走的是硬编码 `/api/plug/...`。
- ⚠️ 语义风险：垫片是"通用垫片"，把插件身份硬编码进 URL 推断，等于把 iframe 桥的职责搬过来；
  若哪天 iframe 改成跨源/嵌套，`location` 会变。取舍：**可以 A+B 都做**（A 治 qzone，B 治 together），
  但只做 B 会漏掉 qzone。

### 选项 C：给兜底路由的保留前缀守卫补日志（可诊断性）

`plugin_pages_web.py:190-192` 目前**静默 404**，导致本次故障在日志里零痕迹。

- ✅ 不改变任何行为，只让下一次同类问题**立刻可见**（符合本项目铁律「过滤/丢弃分支必须留日志」）。
- ⚠️ 取舍：它挡的是**框架命名空间**（`/api/*`、`/static/*`），流量可能包含扫描器噪音
  → 建议打 `WARNING` 但**限流/去重**，或只记 `plugin_dir`，别把整条路径灌进日志。
- 只做 C 不解决问题，但**建议任何方案都带上它**。

### 选项 D：把 `api` 从 `RESERVED_PREFIXES` 移除

- ❌ **不推荐**。那样兜底路由会去吃掉**整个 `/api/*`** 命名空间（包括 `/api/v1/...`），
  与框架路由的优先级关系会变得非常脆弱。当前这条守卫的存在是**对的**；
  缺的是 `/api/plug` 这条**精确**路由（选项 A），不是把守卫拆掉。

### 选项 E：给 `qzone-companion` 注入 fetch 拦截 / 改写 `API` 常量

- ❌ **不推荐**。垫片无法改写插件 JS 里的 `const`；要做只能在服务端注入时改写 HTML/JS 文本，
  属于"改插件的产物"，脆弱且难维护，且与"插件零改动"的既定设计目标冲突。

### 选项 F：向插件作者提 issue，让 `qzone-companion` 改用桥 / 加候选重试

- 治本但**周期不可控**，且我们**本来就该兼容 `/api/plug`**（真 AstrBot 有这条）。
- 可作为 A 落地后的长期项，不作为唯一手段。
