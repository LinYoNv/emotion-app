## 0. 排障前必须记录的 7 项（`bug-fixing.md:16-24`）

不记这 7 项就开始改，等于放弃复现能力。**先记录，再动手。**

- [ ] **插件与宿主版本** —— 【本项目】`emotion_app` 的 git commit + 兼容层版本 +
      实际加载的插件目录（`data/plugin_src/`，不是 `/opt/astrbot/data/plugins`）
- [ ] **发生时间（带时区）** —— 【本项目】`2026-10-08 15:20 Asia/Shanghai`
      🔴 **必须带日期**：`logs/serve.out` 是 `nohup >>` 追加的、横跨多天，
      只有 `HH:MM:SS` 判不出是哪次运行（2026-10-08 已修 TextFormatter 补上日期）
- [ ] **入口与对象** —— 面板页名 / 会话 id / 平台；ID **只留末两位或哈希**
- [ ] **预期与实际** —— "应在 X 情况下做 Y；实际做了 Z"
- [ ] **变更范围** —— 本次只改了**哪一个**字段/参数，旧值 → 新值
- [ ] **运行证据** —— 面板日志页摘要 / `logs/serve.out` 对应时间段 / 会话 id
- [ ] **外部影响** —— 是否触发了**真实发送** / TTS / 生图 API / 数据导入
      （【本项目】生图会**真扣上游额度**，别说"只是测一下"）

## 1. 证据采集顺序（`bug-fixing.md:28-40`）

1. 先确认要改的是**哪一类**：面板运行配置 / 用户·群资料 / 插件配置字段
2. 【本项目】打开**面板「日志」板块**（内存环形缓冲，已脱敏）→ 找**问题类别 + 摘要**；
   需要完整历史再去看 `logs/serve.out`
3. 取**第二份**证据（主动消息 → 会话页 / 模型 → 设置页 / 预算 → 日志页的 Token 相关行）
4. 按**时间 + 对象**查完整链路 —— ⚠️ **只贴最后一行通常会丢失实际 Provider、
   回退、请求 URL 分类和前置拦截原因**（`troubleshooting.md:38`）
5. **一次只改一个**开关或参数 → 保存 → 刷新 → **回到同一页确认"实际值"**
6. 用**一个应成功样本 + 一个应被拦截样本**验收，**两者都过**才继续开启下一项能力

> ⚠️ 【本项目】第 4 步的工具：
> ```bash
> .venv/bin/python tools/log_triage.py --since-last-restart   # 只看最后一次运行周期
> .venv/bin/python tools/log_triage.py --top 15               # 全文 Top 15（带日期反推）
> ```
> **为什么必须切片**：实测 `serve.out` 里最"吓人"的那几条（403 / 不是 JSON）
> **全部止于 09-29**，而服务已连续跑 9 天 —— 不看日期就会把**历史残留**当成当前问题。

## 2. 🔴 十层检查顺序（`troubleshooting.md:12-21`，从外到内）

**这是全文最有价值的一页。** 排障时**按顺序**走，不要跳层 —— 跳层最容易在
"第 9 层网络"上耗掉半天，而真因在第 2 层。

| # | 检查 | 【本项目】怎么查 |
|---|---|---|
| 1 | 插件是否**成功加载**、版本与**实际加载目录** | 启动日志 `插件已挂载 {"loaded": N, ...}`；`GET /api/v1/plugins` |
| 2 | 发送者**真实 ID、平台、适配器实例、UMO** | 会话页的 umo；⚠️ `default` 是**全局兜底**，不是某个人的 |
| 3 | 权限或名单；**普通私聊与主动联系权限分开判断** | 插件配置里的 `proactive_*`；⚠️ 这两者**不是一回事** |
| 4 | **父开关和条件子项**是否同时满足 | 例：开主动消息要 `default_proactive_enabled` + 该用户 `proactive_daily_limit > 0` |
| 5 | 实际任务选了哪个 **Provider / 模型 / 超时 / 限额 / 回退** | 日志 `调用上游(流式) {"model": ...}`；⚠️ 不是 `run.sh check` 那个启动值 |
| 6 | 任务是否产生、**卡在哪个时间窗或闸门** | 主动消息的 `reason=` 字段（如 `quiet_care` / `morning_greeting`） |
| 7 | 当前**平台是否支持**目标动作 | 我们目前只有 `webchat` |
| 8 | 外部插件是否**成功加载并暴露接口** | 【本项目】`_private_companion_api()` 这类跨插件调用（见 §5） |
| 9 | 网络、认证、额度、端点协议、代理 | 上游 403/504 —— **先确认平台侧是否有限额**，别急着改代码 |
| 10 | JSON/SQLite 是否**只读、损坏、被锁或迁移失败** | `data/emotion.db` 的 WAL；`data/plugins/**/*.json` |

## 3. 🔴「开关打开 ≠ 会执行」的门槛链（`bug-fixing.md:92`）

wiki 反复用"必须**同时**通过"的措辞。**这是"配了却没生效"类问题的通用模型。**

**主动消息**必须同时通过：

```
全局调度 → 用户权限 → 投递路由 → 时间/额度 → Provider → 发送前复核 → 平台发送
```

展开核对单（`troubleshooting.md:59-68`）：

- [ ] 目标用户**已开启主动联系权限**
- [ ] 已绑定**真实 UMO**，路由指向**正确**的会话
- [ ] `max_daily_messages` **> 0**（**0 = 停止候选和发送**）
- [ ] 用户级、关系级、状态级额度**均不为 0**
- [ ] 不在**免打扰 / 休息 / 繁忙 / 未回应退避**
- [ ] 候选存在且在**有效时间窗**，未被重复合并
- [ ] **主动人格判断、发送前复核、平台发送**分别通过
- [ ] **Token 硬限额未达到**（`live` **只忽略软降载，不忽略硬限额**）

⚠️ 两条明确的反例提醒：
- 「**不要把"日程已经生成"当作"必然形成可发送候选"**」（`troubleshooting.md:70`）
- 「**不要把候选生成成功改写成已触达**」（`bug-fixing.md:109`）

**"候选很多但不发送"要区分的 16 种状态**（`troubleshooting.md:74`）：
尚未到窗口 / 已过期 / 去重·合并 / 用户拒绝 / 关系·互动状态 / 免打扰 / 休息·繁忙 /
未回应 / 软限降载 / 硬限拦截 / 人格判断 / 终审 / 投递路由 / 核心发送 / 平台兜底。

⏱ 「真实发送测试可能在**约一分钟后**执行。**测试后不要立刻反复点击**」
（`troubleshooting.md:76`）—— 我们实测到的链路同样是"约 60 秒后"。

🔴 **外部插件联动**（`media-integrations.md:275`）必须同时满足：
外部插件成功加载并启用 → 运行接口契约兼容 → 本方策略允许 → 当前平台支持。
**「只有目录存在不算可用」** —— 【本项目】这条我们**踩过**：
`ConversationManagerPort` 契约写错 ⇒ 端口**从第一天起就是 None 且无人能实现**（第九轮）。

## 4. 🔴「什么时候算修复完成」5 条硬判据（`bug-fixing.md:222-228`）

**改完必须逐条过一遍。任一条不满足 = 没修完。**

- [ ] **现象消失**：原始失败样本按预期完成，**或按安全边界留下明确拦截原因**
      （"有明确原因地拒绝"**也算修好**；静默什么都不做**不算**）
- [ ] **边界保留**：白名单、权限、免打扰、额度、内容和平台限制**没有被"修复"绕过**
- [ ] **可解释**：面板和日志能指出**实际配置、Provider、候选阶段或错误分类**
- [ ] **可回退**：配置迁移包和数据备份仍可用；涉及 SQLite 时**保留完整 WAL/SHM**
- [ ] **无串线**：另一用户、群、人格、Bot 实例和另一套页面入口**没有被改变**

> ⭐ 这 5 条与本项目「**判据必须能失败 + 反例样本**」是同一套思路 ——
> 值得作为**每次收尾的自检清单**。
> 【本项目】对应做法：① 反向验证（把修复撤掉，判据必须红）
> ② 注入验证（`tools/inject_*_check.py`）③ 还原后 `diff` 逐字节一致。

## 6. 🔴 排障动作的红线（**不要做的事**）

- ❌ 重装 / 清空记忆 / 删除 SQLite（`bug-fixing.md:10`）
- ❌ 用**不同测试的最后一行**互相拼接日志（`bug-fixing.md:54`）
- ❌ **在服务仍写入时复制单个 `.db`**（`bug-fixing.md:168`）
      —— 【本项目】实测过同型坑：拿 `sha256sum` 当完整性判据会把**正常运行**误报成异常，
      正确判据是**查段数**（见 `docs/GAP_TO_GOAL.md` §7）
- ❌ 手工复制/改名/生成 `pages/????` 目录（`bug-fixing.md:65`）
- ❌ 把**列表字段**改成带逗号的单字符串（`bug-fixing.md:87`）
- ❌ 用降低额度掩盖**重复路由**（`troubleshooting.md:173`）
- ❌ 仅凭**插件目录**判断扩展可用（`media-integrations.md:275`）
- ❌ 通过**伪造主要用户 / 关闭隐私保护 / 放宽跨用户边界**绕过限制（`persona-users.md:124`）
- ❌ 面板 TTS 测试**会真实发送语音**，不要在不确定时点（`troubleshooting.md:155`）
      —— 【本项目】同理：**生图测试会真扣上游额度**

**不应公开的诊断内容**（`troubleshooting.md:258-263`）：
API Key / Cookie / Authorization / 自定义请求头 · 完整 QQ、openid、UMO、群 ID ·
天气精确坐标 · 屏幕截图 · 私聊与长期记忆原文 · 夹层密码 · 上传图与参考图 ·
带敏感 section 的配置导出。
